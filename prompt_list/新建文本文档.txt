  - trade_cal 在 SDK 路径下出现 shape=(0,0)、columns=[] 的异常表现
- 后来验证：
  - 直接 HTTP 调用 Tushare API 可正常返回 code / fields / items
- 当前结论：
  - 关键采集统一走 HTTP 直连 provider
  - 不要再建议把核心采集逻辑切回 SDK 主路径

3. 不要把 Tushare 的 502 误判为我本地代码或文件路径错误
- 我们已验证：
  - stock_basic / daily / daily_basic 等接口会偶发 HTTP 502
  - 这是服务端/网关抖动，不等于本地 SQLite、路径、.env 有问题
- 当前正确处理方式：
  - retry
  - 小批次
  - 分片拉取
  - 局部容错
  - 可重跑补齐
- 不要因为 502 就让我重做数据库或重建项目结构

4. 不要再采用“大区间一次性硬跑”的思路
- 我们已经踩过：
  - 整月甚至更大窗口的 daily / daily_basic 回填很容易因为 502 导致过程极慢、局部失败或被我手动中断
- 当前结论：
  - 默认采用小批次：
    - 快速验证：1 个交易日
    - 小批回填：3 个交易日
    - 中批回填：5 个交易日
  - 不要默认整月盲跑

5. 不要把“局部分片失败”当成“整条链路不可用”
- 我们已经验证：
  - stock_basic / daily / daily_basic 经常出现 PARTIAL_SUCCESS
  - 但已有成功分片写入数据库，而且 upsert 可重复补齐
- 当前正确判断：
  - PARTIAL_SUCCESS 不是系统失效
  - 应进入 gap audit + repair，而不是推翻架构

6. 不要再盲目整段重跑，必须优先 gap audit
- 我们已经建立：
  - data_gap_audit_pipeline.py
  - repair_daily_gaps_pipeline.py
- 当前正确流程：
  - 先审计缺口
  - 再补指定缺口日期
  - 再重建 std_equity_daily
- 不要再在没审计的情况下盲目重跑整月

7. 不要把 std_equity_daily 当成最终研究成品
- 当前 std_equity_daily 的定位是：
  - 桥梁层
  - 标准化研究输入层
- 它不是：
  - 最终特征层
  - 最终 Qlib 专用格式
  - 最终执行层输入
- 当前构建原则：
  - 以 ods_daily 为基表
  - left join ods_daily_basic
  - left join ods_adj_factor
  - join std_security_master
  - 允许局部字段为空，后续通过补洞补齐
- 不要要求当前 std_equity_daily 已经“完全成品化”

8. 不要因为 std_equity_daily 中部分字段为 None 就误判 builder 错误
- 我们已经确认：
  - 若某日 ods_daily_basic 未补齐，则 turnover_rate / pe_ttm 等字段可为空
  - 这是桥梁层在当前阶段的刻意设计
- 当前正确理解：
  - 行情先落桥梁层
  - 估值字段后续补齐
  - 不是 builder 失败

9. 不要再把 stock_basic 放进 daily update 的主链路
- 当前 V1 daily_update_pipeline 的正确策略是：
  - 刷新 trade_cal
  - 重建 std_calendar
  - 修复最近窗口内的 daily / daily_basic / std 缺口
- stock_basic 暂不放入每日更新主链路，避免把高波动、高失败率任务塞进日更流程

10. 不要忽略 scheduler 的运行方式
- run_scheduler.bat 不是“一次性脚本”，而是常驻调度器启动入口
- 只要窗口还开着、进程还在，它会每天重复执行
- 当前约束：
  - 不要同时启动多个 scheduler 进程
  - 调试阶段优先用：
    python -m src.scheduler.scheduler_runner --run-once ...
  - 常驻阶段再用 run_scheduler.bat

11. 不要忘记如何停止 scheduler
- 已确认：
  - 最干净的停法是在原窗口 Ctrl+C
  - 找不到窗口时，可先用 CMD 查询 python 进程及命令行，再按 PID 杀掉
- 不要默认直接 taskkill /IM python.exe，除非确认没有别的 Python 任务

12. 不要误解在 (.venv310) 里编辑/创建文件
- 我们已经确认：
  - 在已激活 .venv310 的 CMD 中编辑、创建、运行项目文件是完全正常的
  - 这不会把项目文件写到虚拟环境目录里
- 后续不要再把“在 venv 里写文件”当成潜在问题

13. 不要忘记历史上出现过的初始化坑
- 我们已经踩过：
  - raw 和 standardized 的索引 SQL 不能混在一个文件里对两个库通用执行
- 当前结论：
  - raw 索引和 std 索引必须拆分
  - 不要再把 create_indexes.sql 混用回去

14. 不要把中断运行后的状态误读为系统没执行
- 我们已经遇到：
  - 某些任务执行中已写入部分数据，但由于用户中断，job_runs 不一定在最开始版本里留下完整状态
- 当前结论：
  - 判断任务结果要同时看：
    - job_runs
    - 表中实际行数
    - 覆盖交易日数
  - 不能只看某一个日志点

15. 后续所有建议，都必须优先复用现有有效模式
- 已验证有效的模式包括：
  - HTTP 直连 provider
  - 小批回填
  - gap audit
  - repair
  - upsert
  - daily_update_v1
  - scheduler_runner
- 不要随意重构成另一套完全不同的流程
